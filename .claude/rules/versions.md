# Versions and dependencies

- Dependency versions are changed by Renovate, not by hand — except when the user asks to update to the latest: then every affected dependency is bumped to its latest published version by hand, in one go, and that round does not wait for or mix with Renovate.
- `@ethberry/eslint-config` stays on the 5.x line: 6.x is ESLint 10, which eslint-plugin-react does not support yet. A fix to the shared config ships as a 5.x patch; repository-specific settings go into the repository's own `eslint.config.mjs`.
- A major waits for approval in the Dependency Dashboard; approving it is a decision, not a routine merge. A manual version change needs the user's explicit decision and says so in the commit.
- Exact versions in `dependencies` and `devDependencies` (`save-exact`); ranges (`^`) only in `peerDependencies`.
- **A peer range is one `^` range, never an OR** (user decision 2026-11-19, the whole organisation): `"react": "^19.0.0"`, `"@ethberry/provider-api": "^10.1.0"`, not `"^8.0.0 || ^9.0.0 || ^10.0.0"`. The range starts at the lowest version the package is built and tested against (its devDependency) and covers that one major. A new major of the peer is adopted by changing the range to the new major, which is a major of our package. An existing `||` range is replaced when its package is next touched.
- The runtime is Node 26 everywhere: `.nvmrc`, `engines.node: ">=26"`, Docker images and CI `node-version`. The runtime version is changed by hand, together in all those places.
- A version that is deliberately held back (a major that breaks tests, a library whose new major needs a tool we do not use) has a Renovate limit (`allowedVersions`) with a `description`, and an ADR in the repository that pins it.
- **The lockfile is committed** (user decision 2026-11-14): no `package-lock=false` in `.npmrc`, `package-lock.json` is in the repository, and installs use `npm ci`. Exact versions in `dependencies` pin only what we declare; without a lockfile every clean install re-resolves the transitive `^` ranges of our dependencies and can pull a version published after our pins — in framework that silently installed a second `@mui/x-data-grid` through `-premium` → `-pro ^9.17.0` and broke the build. A Renovate PR updates the lockfile together with the manifests; a lockfile conflict is resolved by rebuilding it from the base branch, never by hand-editing it.
- **A monorepo installs through npm workspaces** (user decision 2026-11-13, for every monorepo): `"workspaces"` in the root `package.json` and one `npm i` / `npm ci` at the root. `lerna bootstrap`, with or without `--hoist`, is not used; where lerna stays it only runs tasks and publishes. A hoisting bootstrap makes the install order load-bearing — a plain root `npm i` then wipes the hoisted packages and the build fails on a package that is right there in the repository.
- **Adopting a dependency update is verified at the consumer, not only built.** Before merging a PR that raises versions (Renovate's or your own): `npm ls <package>` shows exactly one copy of every package that holds shared state (the `packages` rule lists them) — a second copy is a second React context or metadata registry, which a build and unit tests cannot see; one page of each app is opened in a browser; and the app's end-to-end tests run on **this** PR, not on a later one. A nested copy is never papered over with npm `overrides`, `resolutions` or a dedupe: it means a published package declares shared state as its own dependency, and that package is fixed instead (the `packages` rule). With `legacy-peer-deps=true` a peer is not installed at all, so a package that declares it as a peer cannot bring a second copy.
- `@ethberry/*` packages come from GitHub Packages (`https://npm.pkg.github.com/`); the consumer maps the scope and holds a token with `read:packages` outside the repository. Tokens are never committed.
- A library that owns a React context, a DI token or a module-level singleton (forms, providers, wagmi, react-query, Nest modules) is a `peerDependency` of the packages that use it, never a pinned `dependency`: two installed copies mean two contexts. The consumer declares every peer in its own `dependencies` in the same exact version across apps.
