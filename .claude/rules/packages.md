# Published packages

- **Levels.** A package depends only on packages of lower levels; releases go bottom up. Code that is not React or not Nest-specific belongs to the lowest level that can hold it.
- **Drop-in families.** A base package defines the contract (context, hooks, types, DI token); plugins with a suffix (`-firebase`, `-s3`, `-gcp`, `-jwt`, …) implement it with the same export names and props, all options optional with defaults from env. Switching the implementation is a change of the package name in one place (the provider tree or the module import). Code imports the base package unless it needs something only the implementation has. New families follow this; existing families that do not yet (different export names, required options) are follow-ups in the plan file, not a pattern to copy.
- **Extensions.** A package that extends a lower-level package for a domain (the `-eth` packages: blockchain entities, inputs, validators) re-exports that base package in full, so its consumers need one import. Implementation plugins of a drop-in family do not re-export the base package.
- **Boundaries.** Data hooks do not depend on UI packages. Copies of the same component across plugins are a finding: move the shared part into the base.
- **Module format.** ESM only (`"type": "module"`, `nodenext`, `.js` in relative imports). Exception: packages of Solidity contracts and their Hardhat 2 tests stay CommonJS (Hardhat 2 runs them through ts-node), until Hardhat 3. Never `export * from` a CommonJS package: since Node 23 the namespace contains a `"module.exports"` key, and `require(esm)` on Node 24 and later returns it instead of the module. Re-export the needed names explicitly, and test `require()` and `import` of the built `dist` in a separate Node process.
- **Releases.** Workspaces install the packages (`npm ci`); lerna runs scripts and releases (`lerna version --conventional-commits`, `lerna publish`), never `lerna bootstrap`. A breaking change of a public export, a new required peer or a removed re-export is a major; widening a type or a peer range is a minor or patch.
- **A package changes only for a consumer that needs it.** A defect, a stale peer, a missing test, an inconsistency — found by a check or by reading — is recorded in the plan file and left there until a consumer (an application, a site, the user) names what it needs. A package is not released because something in it changed; it is released because someone is waiting for it. Every major costs a release plus adoption work in every consumer, so a fault no consumer can reach is debt to record, not work to do. "So it cannot happen again" is not a consumer: the check that found it already prevents the repeat.
- **Shared state is a peer, never a dependency.** A package that owns a React context, a Nest DI token, a router, a store or a module-level singleton (react, react-router, react-intl, react-hook-form, emotion, notistack, lexical, wagmi/viem, firebase, supabase, `@nestjs/*`, typeorm, rxjs, and our own `@ethberry/provider-*`, `nest-js-module-*`, `mui-form`, `mui-inputs-file`, `redux`, `history`, `license-*`) is a `peerDependency` with a range plus an exact `devDependency`. Pinning it in `dependencies` installs a second copy at a consumer whose version differs, and the app then reads the empty context: a pinned `@ethberry/provider-license` in `mui-dialog` 6.0.0 crashed every admin-ui list page on 2026-11-13. The second reason for a peer is the consumer's own install: a third-party library the consuming application also installs (viem, zod, date-fns…) is a peer plus an exact devDependency even when it holds no state, because a pinned copy in a published package pins the application's version — the app cannot raise it without our release, and raising it anyway installs a second copy. Exception: `nest-js-module-license` and `provider-license` keep viem as an ordinary dependency (user's decision 2026-11-25, ADR 0001 in license-packages): nearly every package needs the license module, and with `legacy-peer-deps` a viem peer would have to be declared by each of them. A factory with no state that the application does not install itself (for example `@emotion/cache`) is an ordinary dependency. The check is `check-peers.mjs` (ethberry-deps scripts), run in the local checks before a PR and before every release; a consumer also verifies with `npm ls <package>` that only one copy is installed.
- **Removing a package.** A package is removed only when it is empty after regrouping, or by the user's decision. Before removing it, push a **lightweight** tag `archive/<package>` on the last commit that has it (`git tag archive/<package> <sha>`, never `-a` / `-m`); restore with `git checkout archive/<package> -- <path>`. The tag must be lightweight: lerna's change detection runs `git describe` without `--match`, so an annotated `archive/*` tag is taken for the last release and the next release silently misses everything committed before it. What the message used to hold (the last published version, why it went) goes into the removal PR instead. Published versions stay usable.
- **Publishing.** The lerna monorepos publish to GitHub Packages only, always from an obfuscated `dist` (`npm run obfuscate` before publish); jest runs against obfuscated sibling `dist`s, so obfuscation is never the explanation for a failing test. The single public repositories (nestjs-router-eth, nestjs-router-solana, nestjs-router-ton, nestjs-sqs, mui-lexical) publish plain source to npmjs. Releases run locally from the owner's machine (the Actions budget is spent): Packages publishes the package repositories, Contracts the contract packages; the npmjs part needs the user's token.
- **Unused packages.** A package no consumer uses is not deleted (see removing below) and not tested: test effort goes to what a consumer stands on. Before testing a group, list each package's consumers.
- **License logic is intended.** nest-js-module-license's code removal on a revoked license and the license provider's nonce handling are product behaviour: not a finding, not a question, not a change; reviews of license-packages cover packaging, peers and build only.
- **Not consumers.** `coart` and `body-shop` are archived usage examples: no compatibility, migration notes or work for them.
- **Forms.** A form validates with the schema but submits the values its inputs hold; it never submits the schema's transformed output.
