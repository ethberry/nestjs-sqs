# Published packages

- **Levels.** A package depends only on packages of lower levels; releases go bottom up. Code that is not React or not Nest-specific belongs to the lowest level that can hold it.
- **Drop-in families.** A base package defines the contract (context, hooks, types, DI token); plugins with a suffix (`-firebase`, `-s3`, `-gcp`, `-jwt`, …) implement it with the same export names and props, all options optional with defaults from env. Switching the implementation is a change of the package name in one place (the provider tree or the module import). Code imports the base package unless it needs something only the implementation has. New families follow this; existing families that do not yet (different export names, required options) are follow-ups in the plan file, not a pattern to copy.
- **Extensions.** A package that extends a lower-level package for a domain (the `-eth` packages: blockchain entities, inputs, validators) re-exports that base package in full, so its consumers need one import. Implementation plugins of a drop-in family do not re-export the base package.
- **Boundaries.** Data hooks do not depend on UI packages. Copies of the same component across plugins are a finding: move the shared part into the base.
- **Module format.** ESM only (`"type": "module"`, `nodenext`, `.js` in relative imports). Exception: packages of Solidity contracts and their Hardhat 2 tests stay CommonJS (Hardhat 2 runs them through ts-node), until Hardhat 3. Never `export * from` a CommonJS package: since Node 23 the namespace contains a `"module.exports"` key, and `require(esm)` on Node 24 returns it instead of the module. Re-export the needed names explicitly, and test `require()` and `import` of the built `dist` in a separate Node process.
- **Releases.** Workspaces install the packages (`npm ci`); lerna runs scripts and releases (`lerna version --conventional-commits`, `lerna publish`), never `lerna bootstrap`. A breaking change of a public export, a new required peer or a removed re-export is a major; widening a type or a peer range is a minor or patch.
- **Removing a package.** A package is removed only when it is empty after regrouping, or by the user's decision. Before removing it, push an annotated tag `archive/<package>` on the last commit that has it, with its last published version in the message; restore with `git checkout archive/<package> -- <path>`. Published versions stay usable.
- **Forms.** A form validates with the schema but submits the values its inputs hold; it never submits the schema's transformed output.
